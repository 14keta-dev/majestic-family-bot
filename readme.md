# Majestic Family Bot

Дискорд-бот для подачи заявок в семью на Majestic RP — формы заявок, воркфлоу рассмотрения, автоматическая выдача ролей, учёт отпусков и системы AFK участников.

## Getting Started

Следуя этим инструкциям, вы сможете развернуть копию проекта на локальной машине для целей разработки и тестирования.

### Prerequisites

Требования к программному обеспечению и другим инструментам для сборки, тестирования и развёртывания:

- [Node.js](https://nodejs.org/) >= 20.0.0
- [pnpm](https://pnpm.io/) 11.x (проект использует pnpm как менеджер пакетов)
- PostgreSQL (используется как база данных через `drizzle-orm` / `postgres` / `supabase`)
- Discord Bot Token и Application ID ([Discord Developer Portal](https://discord.com/developers/applications))
- В настройках приложения (вкладка **Bot**) включены привилегированные intents:
  - **Presence Intent**
  - **Server Members Intent**
  - **Message Content Intent**

### Installing

Копирование репозитория:

```bash
git clone https://github.com/14keta-dev/majestic-family-bot
cd ./majestic-family-bot
```

Установка зависимостей:

```bash
pnpm install
```

Настройка переменных окружения — создайте файл `.env` в корне проекта:

```env
DISCORD_BOT_TOKEN=your_bot_token
DISCORD_BOT_CLIENT=your_application_id
DEVELOPER_ID=your_discord_id
PREFIX="!"
DISCORD_GUILD=discord_guild_where_bot_will_operate
DATABASE_URL=postgresql://user.project-ref:password@region.pooler.supabase.com:5432/postgres
WEBHOOK_URL=discord_webhook_for_errors
```

Подробное описание каждой переменной, включая режимы подключения Supabase (session vs transaction pooling), см. в [`.env.example`](.env.example).

Применение схемы базы данных:

```bash
pnpm db:push
```

Регистрация слэш-команд бота на сервере Discord:

```bash
pnpm deploy
```

Регистрация эмодзи бота на сервере Discord:

```bash
pnpm deploy-emojis
```

Запуск в режиме разработки (с автоперезагрузкой):

```bash
pnpm dev
```

После запуска бот появится онлайн на вашем Discord-сервере, и слэш-команды, зарегистрированные через `pnpm deploy`, станут доступны для использования — `/menu`, чтобы запустить систему заявок.

## Configuration

Бот настраивается под конкретную семью через конфигурационные файлы, без изменения основной логики.

### Embed с заявкой

Внешний вид эмбеда с меню подачи заявки (баннер, текст, статус набора) редактируется в:

```
src/embed/family_applications/apply.embed.ts
```

### Поля модального окна заявки

Типы заявок (`APPLY_TYPES`) и поля модального окна, которые видит пользователь при заполнении (`APPLY_FIELDS`), настраиваются в:

```
src/utils/config/family_applications/applyFieldPresets.ts
```

Здесь можно:
- добавлять/изменять поля анкеты (`label`, `placeholder`, `style`, `required`)
- добавлять новые типы заявок с собственным набором полей, ролью для пинга (`pingRole`) и ролями за одобрение (`rewardRoles`)

При старте бот валидирует конфигурацию (`validateApplyConfig`) и упадёт с ошибкой, если тип заявки ссылается на несуществующее поле, превышает лимит полей модалки (`MAX_MODAL_FIELDS`) или содержит дублирующиеся `id`.

После изменения не забудьте перезапустить бота, затем отправьте команду `!famq` (префикс + `famq`) в канале подачи заявок, чтобы опубликовать обновлённый эмбед.

### Система отпусков

Модуль отпусков позволяет участникам временно уходить в неактив с автоматической выдачей/снятием ролей и логированием всех действий в отдельный канал.

Основные настройки (уточните точный путь и формат в вашем конфиге):

- `vacation.vacation_role` — роль, которая выдаётся участнику на время отпуска (и снимается при возвращении, кике или автоистечении).
- `vacation.controlled` — режим модерации:
  - `true` — заявка на отпуск требует одобрения модератором (`Принять` / `Отклонить`);
  - `false` — отпуск оформляется сразу же после заполнения модального окна.
- `logs.vacation_log` — ID канала, куда публикуются заявки на отпуск и последующие события по ним (одобрение/отклонение, самостоятельное возвращение, принудительное завершение, автоматическое истечение).

Панель для участников (`Взять отпуск` / `Вернуться` / `Список`) публикуется через embed в `src/embed/vacation/vacation.embed.ts` — там же настраивается баннер и текст, аналогично `apply.embed.ts`.

Активные отпуска автоматически завершаются, если истёк срок (`estimated_end`), а участник не вернулся и не был снят вручную — это делает фоновый sweeper (`src/utils/vacation/expirySweeper.helper.ts`), запускающийся каждые 5 минут. Событие также фиксируется в лог-канале.

Заявка на отпуск также блокируется от повторной одновременной обработки: пока один запрос на отпуск для пользователя выполняется, повторные попытки словят `Vacation_write_in_progress_error`, а конкретная запись — `Vacation_entry_locked_error`, если по ней уже идёт действие (например, рассмотрение модератором).

### Система AFK

Модуль AFK позволяет участникам временно отмечаться как неактивные на срок до 24 часов, с автоматическим снятием по истечении времени и полным логированием в отдельный канал.

В отличие от заявок и отпусков, AFK **не требует ручного редактирования конфиг-файлов** — настройка происходит полностью через Discord-интерфейс (панель управления → кнопка AFK → мастер настройки), при условии, что у пользователя есть право `Manage Guild`.

**Первичная настройка:**

1. Откройте панель управления ботом и выберите раздел AFK.
2. Если система ещё не настроена, откроется мастер настройки с двумя выборами канала:
   - **Канал панели AFK** (обязательно) — куда будет отправлено сообщение с кнопками `Уйти в AFK` / `Список` / `Выйти из AFK`;
   - **Канал логов AFK** (необязательно) — куда будут публиковаться вход/выход/кик/автокик. Если не указан, бот автоматически создаст категорию `bot-logs` (если её ещё нет) и канал `afk-logs` внутри неё, скрытые от `@everyone`.
3. По кнопке `Подтвердить` конфигурация сохраняется, панель публикуется в выбранный канал.

Настройки хранятся в конфиге как `AFK.panel_channel`, `AFK.panel_message` и `logs.afk_log`. Повторное открытие раздела AFK в панели управления (когда система уже настроена) откроет экран `Управление AFK` с текущими значениями и кнопкой `Изменить Настройки` для повторного запуска мастера в режиме редактирования.

> Черновики настройки живут в памяти процесса (`draft_afk_store.ts`) и автоматически удаляются через 30 минут неактивности — если мастер настройки не был завершён, его придётся открыть заново.

**Формат длительности AFK:** `30m`, `1h`, `12h`, `1h30m` (регистр не важен, минимум 30 минут, максимум 24 часа) — валидируется при отправке модального окна `Уйти в AFK`.

**Автоматическое снятие:** фоновый планировщик `src/utils/AFK/afk_autokick_scheduler.ts` проверяет истёкшие записи каждую минуту и снимает AFK-статус автоматически, публикуя запись в лог-канал с пометкой "снят системой" — так же, как и при ручном выходе (`Выйти из AFK`) или принудительном кике модератором через кнопку под записью в логах.

### Локальное хранилище (AFK и отпуска)

Записи AFK и отпусков хранятся не в основной PostgreSQL-базе, а в отдельном локальном JSON-хранилище — `src/utils/db/local/local_db.ts` (класс `JsonDb`).

Каждая сущность хранится в собственном файле в директории `db/` в корне проекта, которая создаётся автоматически при первом обращении:

- `db/afk-db.json` — записи AFK (`AFK_schema`, `src/utils/AFK/afk_store.ts` — уточните актуальный путь в вашем проекте);
- `db/vacation-db.json` — записи отпусков (`Vacation_schema`, `src/utils/vacation/vacation_store.ts` — уточните актуальный путь в вашем проекте).

Каждая запись получает уникальный `id`, сгенерированный через [`nanoid`](https://github.com/ai/nanoid). Записи в памяти кэшируются как `Map`, а запись на диск выполняется атомарно (через временный `.tmp`-файл с последующим `rename`) и последовательно — конкурентные вызовы `set`/`update`/`delete` для одной и той же БД ставятся в очередь, чтобы избежать гонок при записи.

`JsonDb<T>` предоставляет базовый набор методов: `get`, `getAll`, `has`, `find`, `filter`, `query` (по точному совпадению полей), `queryContains` (по вхождению значения в массив), а также асинхронные `set`, `update`, `delete`.

> Директория `db/` создаётся автоматически и не требует ручной настройки. При необходимости добавьте её в `.gitignore`, если она ещё не туда включена — файлы содержат данные конкретного сервера (Discord ID участников, причины отпусков/AFK и т.д.) и не должны попадать в репозиторий.

## Deployment

1. Соберите проект:

   ```bash
   pnpm build
   ```

2. Запустите собранную версию:

   ```bash
   pnpm start
   ```

3. Для деплоя слэш-команд и/или кастомных эмодзи на боевой сервер:

   ```bash
   pnpm deploy
   pnpm deploy-emojis
   ```

   Для предварительной проверки без реальных изменений:

   ```bash
   pnpm deploy-emojis:dry
   ```

Убедитесь, что переменные окружения (`.env`) на продакшн-сервере настроены отдельно от локальных и что `DATABASE_URL` указывает на боевую базу данных. Также убедитесь, что директория `db/` (локальные JSON-записи AFK и отпусков) сохраняется между деплоями — например, через volume/persistent storage, иначе активные AFK-статусы и отпуска будут потеряны при пересоздании контейнера.
