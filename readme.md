# Majestic Family Bot

🍺 [Поддержать проект / Buy Me a Beer](https://buymeacoffee.com/keta88)

Дискорд-бот для подачи заявок в семью на Majestic RP — формы заявок, воркфлоу рассмотрения, автоматическая выдача ролей, учёт отпусков, системы AFK участников, персональные каналы участников (бэкпаки), временные голосовые каналы и система организации сборов (МП) с учётом участников и откатов.

## Getting Started

Следуя этим инструкциям, вы сможете развернуть копию проекта на локальной машине для целей разработки и тестирования.

### Prerequisites

Требования к программному обеспечению и другим инструментам для сборки, тестирования и развёртывания:

- [Node.js](https://nodejs.org/) >= 20.0.0
- [pnpm](https://pnpm.io/) 11.x (проект использует pnpm как менеджер пакетов)
- PostgreSQL (используется как база данных через `drizzle-orm` / `postgres` / `supabase`)
- Discord Bot Token и Application ID ([Discord Developer Portal](https://discord.com/developers/applications))
- В настройках приложения (вкладка **Bot**) включены привилегированные intents:
  - **Presence Intent**
  - **Server Members Intent**
  - **Message Content Intent**

### Installing

Копирование репозитория:

```bash
git clone https://github.com/14keta-dev/majestic-family-bot
cd ./majestic-family-bot
```

Установка зависимостей:

```bash
pnpm install
```

Настройка переменных окружения — создайте файл `.env` в корне проекта:

```env
DISCORD_BOT_TOKEN=your_bot_token
DISCORD_BOT_CLIENT=your_application_id
DEVELOPER_ID=your_discord_id
PREFIX="!"
DISCORD_GUILD=discord_guild_where_bot_will_operate
DATABASE_URL=postgresql://user.project-ref:password@region.pooler.supabase.com:5432/postgres
WEBHOOK_URL=discord_webhook_for_errors
NODE_ENV="production"
```

Подробное описание каждой переменной, включая режимы подключения Supabase (session vs transaction pooling), см. в [`.env.example`](.env.example).

Применение схемы базы данных:

```bash
pnpm db:push
```

Регистрация слэш-команд бота на сервере Discord:

```bash
pnpm deploy
```

Регистрация эмодзи бота на сервере Discord:

```bash
pnpm deploy-emojis
```

Запуск в режиме разработки (с автоперезагрузкой):

```bash
pnpm dev
```

После запуска бот появится онлайн на вашем Discord-сервере, и слэш-команды, зарегистрированные через `pnpm deploy`, станут доступны для использования — `/menu`, чтобы запустить систему заявок.

## Configuration

Бот настраивается под конкретную семью через конфигурационные файлы, без изменения основной логики.

### Embed с заявкой

Внешний вид эмбеда с меню подачи заявки (баннер, текст, статус набора) редактируется в:

```
src/embed/family_applications/apply.embed.ts
```

### Поля модального окна заявки

Типы заявок (`APPLY_TYPES`) и поля модального окна, которые видит пользователь при заполнении (`APPLY_FIELDS`), настраиваются в:

```
src/utils/config/family_applications/applyFieldPresets.ts
```

Здесь можно:
- добавлять/изменять поля анкеты (`label`, `placeholder`, `style`, `required`)
- добавлять новые типы заявок с собственным набором полей, ролью для пинга (`pingRole`) и ролями за одобрение (`rewardRoles`)

При старте бот валидирует конфигурацию (`validateApplyConfig`) и упадёт с ошибкой, если тип заявки ссылается на несуществующее поле, превышает лимит полей модалки (`MAX_MODAL_FIELDS`) или содержит дублирующиеся `id`.

После изменения не забудьте перезапустить бота, затем отправьте команду `!famq` (префикс + `famq`) в канале подачи заявок, чтобы опубликовать обновлённый эмбед.

### Роль семьи

Роль, по которой бот определяет состав семьи (используется, например, системой папок для подсчёта участников без персонального канала), задаётся командой:

```
!family @Роль
```

(префикс + `family`, требуется право `Manage Guild`, указывается ровно одна роль). Значение сохраняется в конфиге как `family_role`.

### Система отпусков

Модуль отпусков позволяет участникам временно уходить в неактив с автоматической выдачей/снятием ролей и логированием всех действий в отдельный канал.

Основные настройки (уточните точный путь и формат в вашем конфиге):

- `vacation.vacation_role` — роль, которая выдаётся участнику на время отпуска (и снимается при возвращении, кике или автоистечении).
- `vacation.controlled` — режим модерации:
  - `true` — заявка на отпуск требует одобрения модератором (`Принять` / `Отклонить`);
  - `false` — отпуск оформляется сразу же после заполнения модального окна.
- `logs.vacation_log` — ID канала, куда публикуются заявки на отпуск и последующие события по ним (одобрение/отклонение, самостоятельное возвращение, принудительное завершение, автоматическое истечение).

Панель для участников (`Взять отпуск` / `Вернуться` / `Список`) публикуется через embed в `src/embed/vacation/vacation.embed.ts` — там же настраивается баннер и текст, аналогично `apply.embed.ts`.

Активные отпуска автоматически завершаются, если истёк срок (`estimated_end`), а участник не вернулся и не был снят вручную — это делает фоновый sweeper (`src/utils/vacation/expirySweeper.helper.ts`), запускающийся каждые 5 минут. Событие также фиксируется в лог-канале.

Заявка на отпуск также блокируется от повторной одновременной обработки: пока один запрос на отпуск для пользователя выполняется, повторные попытки словят `Vacation_write_in_progress_error`, а конкретная запись — `Vacation_entry_locked_error`, если по ней уже идёт действие (например, рассмотрение модератором).

### Система AFK

Модуль AFK позволяет участникам временно отмечаться как неактивные на срок до 24 часов, с автоматическим снятием по истечении времени и полным логированием в отдельный канал.

В отличие от заявок и отпусков, AFK **не требует ручного редактирования конфиг-файлов** — настройка происходит полностью через Discord-интерфейс (панель управления → кнопка AFK → мастер настройки), при условии, что у пользователя есть право `Manage Guild`.

**Первичная настройка:**

1. Откройте панель управления ботом и выберите раздел AFK.
2. Если система ещё не настроена, откроется мастер настройки с двумя выборами канала:
   - **Канал панели AFK** (обязательно) — куда будет отправлено сообщение с кнопками `Уйти в AFK` / `Список` / `Выйти из AFK`;
   - **Канал логов AFK** (необязательно) — куда будут публиковаться вход/выход/кик/автокик. Если не указан, бот автоматически создаст категорию `bot-logs` (если её ещё нет) и канал `afk-logs` внутри неё, скрытые от `@everyone`.
3. По кнопке `Подтвердить` конфигурация сохраняется, панель публикуется в выбранный канал.

Настройки хранятся в конфиге как `AFK.panel_channel`, `AFK.panel_message` и `logs.afk_log`. Повторное открытие раздела AFK в панели управления (когда система уже настроена) откроет экран `Управление AFK` с текущими значениями и кнопкой `Изменить Настройки` для повторного запуска мастера в режиме редактирования.

> Черновики настройки живут в памяти процесса (`draft_afk_store.ts`) и автоматически удаляются через 30 минут неактивности — если мастер настройки не был завершён, его придётся открыть заново.

**Формат длительности AFK:** `30m`, `1h`, `12h`, `1h30m` (регистр не важен, минимум 30 минут, максимум 24 часа) — валидируется при отправке модального окна `Уйти в AFK`.

**Автоматическое снятие:** фоновый планировщик `src/utils/AFK/afk_autokick_scheduler.ts` проверяет истёкшие записи каждую минуту и снимает AFK-статус автоматически, публикуя запись в лог-канал с пометкой "снят системой" — так же, как и при ручном выходе (`Выйти из AFK`) или принудительном кике модератором через кнопку под записью в логах.

### Система папок (личных каналов)

Модуль папок выдаёт каждому участнику семьи персональный приватный текстовый канал ("портфель") для фиксации откатов, активности и прогресса. Создание, распределение по категориям и удаление каналов бот выполняет автоматически.

Как и AFK, система **настраивается полностью через Discord-интерфейс** (панель управления → раздел "Папки" → мастер настройки), без правки конфиг-файлов, при условии права `Manage Guild`.

**Первичная настройка:**

1. Откройте панель управления ботом и выберите раздел "Управления Портфелям".
2. Если система ещё не настроена, откроется мастер настройки:
   - **Канал панели** (обязательно) — куда публикуется сообщение с кнопкой `Создать`;
   - **Роли модерации** (обязательно, до 25 ролей) — роли, которые дополнительно получают доступ к каждому создаваемому каналу папки.
3. По кнопке `Подтвердить` конфигурация сохраняется, панель с кнопкой `Создать` публикуется в выбранный канал.

Настройки хранятся в конфиге как `backpack.panel_channel`, `backpack.panel_message` и `backpack.allowed_roles`.

**Создание канала:** по нажатию кнопки `Создать` бот создаёт для участника текстовый канал `backpack・{имя}`, видимый только самому участнику, ролям модерации и администраторам. Если канал уже есть — бот вернёт ссылку на существующий, не создавая новый. Повторные нажатия одним и тем же пользователем, пока предыдущий запрос ещё в обработке, игнорируются (короткий кулдаун).

**Категории:** каналы распределяются по категориям `archive・{N}`, не более 50 каналов в одной категории — при заполнении текущей автоматически создаётся следующая. Если категория была удалена вручную в Discord, оставшиеся в ней каналы (если ещё существуют) переносятся в другую категорию с местом, а сама запись о категории удаляется из локальной базы.

**Удаление канала:** доступно самому участнику или модератору через выпадающее меню `Управления каналом` внутри канала бэкпака. При удалении последнего канала в категории удаляется и сама категория.

**Панель управления (для модераторов):** раздел "Портфель" показывает канал панели, роли модерации, общее число каналов, число участников семьи (см. [Роль семьи](#роль-семьи)) и сколько из них ещё не создали себе канал — с постраничным списком таких участников (кнопка `Без папки (N)`) и кнопкой `Изменить Настройки` для повторного запуска мастера в режиме редактирования.

**Изменение ролей модерации:** если при редактировании настроек список ролей меняется, бот переприменяет права доступа на все существующие категории и каналы папок параллельно с ограничением одновременных запросов к Discord API, сообщая о прогрессе и результате (сколько категорий/каналов обновлено, сколько пропущено — вероятно, удалённых вручную). Пока эта операция выполняется на сервере, повторные подтверждения настроек папок блокируются с предупреждением до её завершения.

**Переотправка панели:** команда `!bacpack` (префикс + `bacpack`, требуется право `Manage Guild`) удаляет старое сообщение панели (если есть) и публикует новое в текущем канале — аналогично `!famq` для заявок.

### Система временных голосовых каналов (Temp Voice)

Модуль Temp Voice позволяет участникам создавать собственные временные голосовые комнаты, заходя в специальный канал-триггер, и полностью управлять ими через панель с кнопками — без участия администраторов.

**Первичная настройка:**

Разверните панель командой `!temp` (префикс + `temp`, требуется право `Manage Guild`) в любом текстовом канале. Команда автоматически создаёт:

- категорию `— · Temp Voice`;
- текстовый канал `┌⚙️ · settings` с панелью управления (кнопки);
- голосовой канал `└➕ · create` — заход в него создаёт новую временную комнату.

Если панель уже была развёрнута ранее, повторный вызов `!temp` сначала удаляет предыдущую категорию/каналы и пересоздаёт всё заново — это позволяет обновить панель без ручной чистки старых каналов.

Настройки сохраняются в конфиге как `temp_voice.category`, `temp_voice.panel_channel`, `temp_voice.create_channel` и `temp_voice.panel_message_id`.

**Создание комнаты:** при заходе участника в канал `└➕ · create` бот создаёт для него отдельный голосовой канал `・комната {имя}` в той же категории и автоматически перемещает участника туда. Владельцем комнаты (`ownerId`) становится создатель.

**Управление комнатой:** доступно владельцу комнаты или пользователю с правом `Administrator`, из канала `┌⚙️ · settings` через кнопки:

| Кнопка | Действие |
|---|---|
| ➕ / ➖ слот | Увеличить/уменьшить лимит участников на 1 (0–99) |
| Открыть/закрыть | Разрешить/запретить вход новым участникам |
| Заглушить/снять | Выдать/забрать server mute конкретному пользователю в комнате |
| Исключить | Забрать доступ на подключение конкретному пользователю (с принудительным отключением, если он сейчас в комнате) |
| Битрейт | Изменить битрейт комнаты (от 8 кбит/с до максимума, доступного по уровню буста сервера) |
| Лимит слотов | Установить точный лимит участников (0 — без лимита, макс. 99) через модальное окно |
| Передать лидерство | Передать владение комнатой (`ownerId`) другому участнику из комнаты |
| Название | Переименовать комнату через модальное окно |
| Выдать доступ | Явно разрешить вход/просмотр конкретным пользователям — снимает как "закрыт", так и "исключён" для выбранных |

**Автоматическое удаление:** когда владелец покидает свою временную комнату (событие `voiceStateUpdate`), бот удаляет канал и соответствующую запись в базе — вручную ничего чистить не нужно. Если бот был офлайн в момент, когда владелец вышел, канал не будет удалён автоматически до следующего события выхода в этом канале.

> Настройка Temp Voice выполняется один раз через `!temp` и не требует правки конфиг-файлов вручную — всё содержимое панели (кнопки, описания, эмодзи) задаётся в коде (`src/commands/prefix/temp.prefix.ts`), а не через Discord-интерфейс, в отличие от AFK и папок.

### Система сборов (МП)

Модуль МП позволяет модераторам организовывать сборы (рейды/ивенты и т.п.): создавать типы сборов с привязкой к конкретным каналам и ролям модерации, публиковать сами сборы с основным и запасным списком участников, набирать участников через реакции в отдельной ветке, рассылать напоминания, а по завершении — архивировать сбор и собирать с основного состава ссылки на «откаты».

#### Типы МП

Типы МП (например, разные виды рейдов) настраиваются через панель управления ботом (раздел "Управление МП"):

- Если ни один тип ещё не создан, раздел сразу открывает модальное окно создания типа.
- Если типы уже есть, открывается список существующих типов с кнопками `Настройки` у каждого и `Добавить МП` внизу.

**Создание/редактирование типа** (`create_mp_modal`) — модальное окно с полями:

- **Названия МП** — уникальное имя типа (мин. 3 символа);
- **Канал создания** — текстовый канал, куда публикуется панель с кнопкой `Создать {название}` для запуска конкретного сбора этого типа;
- **Канал тегов** — текстовый канал, куда публикуется сам эмбед сбора (с `@everyone` и веткой для записи участников);
- **Канал Откатов** — текстовый канал, куда сбор архивируется после завершения;
- **Роли модерации** — до 25 ролей, участники которых (помимо создателя сбора и администраторов) могут управлять сборами этого типа.

При создании названия проверяются на уникальность; сообщение с кнопкой `Создать {название}` публикуется в выбранный канал создания. При редактировании: если название меняется — тоже проверяется на конфликт; если канал создания не поменялся — существующее сообщение с кнопкой редактируется на месте, иначе старое удаляется и отправляется новое в новый канал.

Кнопка `Настройки` у типа показывает текущие каналы, роли модерации и ссылку на сообщение создания, с кнопками `Изменить` (открывает то же модальное окно, предзаполненное), `Удалить` (удаляет сообщение с кнопкой создания и запись из конфига) и `Назад`.

#### Создание конкретного сбора

Нажатие кнопки `Создать {название}` в канале создания открывает модальное окно с полями:

- **Описания** (до 4000 символов);
- **Огран участников** — целочисленный лимит основного списка;
- **Начало** — время в свободном формате `чч:мм дд.мм`, например `14:30 21.08` (парсится `parseFlexibleDateTime`: значения времени и даты можно спутать местами — если одно из чисел явно не подходит как часы/минуты, порядок определяется автоматически; год не указывается — берётся текущий, либо следующий, если указанная дата уже прошла в этом году).

После отправки бот публикует в канале тегов эмбед сбора (`event_tag_embed`) — с `@everyone`-пингом, статусом регистрации, временем начала, описанием, основным списком (`x/лимит`), запасным списком и кнопкой `Управлять списком`, — и открывает под этим сообщением ветку (авто-архивация через 3 дня). Именно в этой ветке участники оставляют сообщение, чтобы заявиться на сбор.

#### Запись участников через реакции

В ветке сбора модератор (создатель сбора, администратор, либо участник с одной из ролей модерации этого типа МП) ставит реакцию на сообщение участника:

- **✅** — добавляет автора сообщения в основной список. Если список уже заполнен, реакция автоматически снимается, а в канал на пару секунд отправляется предупреждение (после чего само удаляется). Если участник был в запасном списке, он оттуда автоматически убирается.
- **⏰** — добавляет автора в запасной список. Если участник уже в основном списке, реакция снимается и ничего не меняется.

Снятие модератором своей реакции убирает участника из соответствующего списка. Реакции от ботов, а также от пользователей без прав на управление этим типом МП, игнорируются без каких-либо уведомлений. После любого изменения списков эмбед сбора в ветке автоматически обновляется.

#### Управление сбором

Кнопка `Управлять списком` на эмбеде сбора открывает тому, у кого есть права, эфемерное меню с действиями:

| Действие | Что делает |
|---|---|
| Редактировать | Модальное окно: изменить описание, лимит участников (нельзя указать меньше числа уже находящихся в основном списке) и время начала |
| Напомнить в ветке | Отправляет в ветку сбора @-упоминания основного списка / запасного списка / обоих (сообщение с напоминанием исчезает через 5 секунд) |
| Напомнить в ЛС | Рассылает участникам основного/запасного/обоих списков напоминание в личные сообщения с указанием времени начала; кнопки блокируются на время рассылки, итоговый статус (сколько успешно / не удалось из-за закрытых ЛС) отображается прямо в панели |
| Открыть/закрыть регистрацию | Переключает статус регистрации сбора и одновременно блокирует/разблокирует саму ветку для новых сообщений |
| Добавить в основной список | Ручной выбор участников через user-select (лимит — оставшиеся свободные места); показывает добавленных, уже состоявших в списке и не поместившихся |
| Добавить в запасной список | Аналогично, без ограничения по числу мест; участников, уже находящихся в основном списке, не добавляет |
| Удалить из основного / запасного списка | Список текущих участников (до 25) в виде select-меню с их именами — выбор для удаления |
| Завершить | Архивирует и закрывает сбор (см. ниже) |

#### Завершение сбора и откаты

По кнопке `Завершить` (после подтверждения) сбор архивируется:

1. Эмбед-архив публикуется в канал откатов этого типа МП, под ним создаётся ветка для откатов (авто-архивация через 7 дней).
2. Оригинальное сообщение сбора в канале тегов удаляется, регистрация закрывается.
3. Всем участникам основного списка рассылается ЛС с кнопкой `Оставить откат`.

Повторное нажатие `Завершить`, пока предыдущий запуск ещё выполняется, игнорируется — защита от двойного клика.

По кнопке `Оставить откат` в ЛС открывается модальное окно со ссылкой; ссылка сохраняется и публикуется в ветку откатов. Если участник уже сдавал откат, кнопка в его ЛС-сообщении отключается — повторная сдача через уже открытую форму просто обновляет сохранённую ссылку.

В самом архивном сообщении доступны ещё две кнопки:

- **Запросить откаты** — повторно рассылает ЛС с кнопкой сдачи тем из основного списка, кто ещё не сдал.
- **Кто залил откаты** — показывает список сдавших (со ссылками) и список ещё не сдавших.

#### Права на управление сбором

Управлять конкретным сбором (реакции в ветке, панель управления, редактирование, завершение и т.д.) может: создатель сбора, любой пользователь с правом `Administrator`, либо участник с одной из ролей, указанных в `Роли модерации` для данного типа МП.

### Локальное хранилище (AFK, отпуска, бэкпаки, Temp Voice и МП)

Записи AFK, отпусков, персональных каналов (папки), временных голосовых комнат и сборов (МП) хранятся не в основной PostgreSQL-базе, а в отдельном локальном JSON-хранилище — `src/utils/db/local/local_db.ts` (класс `JsonDb`).

Каждая сущность хранится в собственном файле в директории `db/` в корне проекта, которая создаётся автоматически при первом обращении:

- `db/afk-db.json` — записи AFK (`AFK_schema`, `src/utils/AFK/afk_store.ts` — уточните актуальный путь в вашем проекте);
- `db/vacation-db.json` — записи отпусков (`Vacation_schema`, `src/utils/vacation/vacation_store.ts` — уточните актуальный путь в вашем проекте);
- записи папок (`src/utils/backpack/backpack.schema.ts`, уточните актуальные имена файлов в вашем проекте) — хранятся в двух отдельных `JsonDb`:
  - категории (`Backpack_category_interface`: id категории и список каналов внутри неё);
  - каналы (`Backpack_channel`: id канала, владелец, категория, id сообщения, даты создания/обновления);
- `db/temp_voice-db.json` — активные временные голосовые комнаты (`Temp_voice_schema`, `src/utils/temp_voice/schema.ts`): `id` канала, `ownerId` и `createdAt`;
- `db/event_db.json` — сборы МП (`EventSchema`, `src/utils/EVENT/event.schema.ts`): тип, создатель, описание, лимит и время начала, основной/запасной списки участников, сданные откаты, id сообщения/ветки/ветки-архива, статус регистрации и временные метки создания/завершения. Мутации списков сериализуются по `id` сбора (внутренняя очередь на запись), чтобы одновременные реакции/действия модераторов не приводили к гонкам; индекс "ветка → сбор" строится в памяти при первом обращении для быстрого поиска отслеживаемых веток по `threadId`.

Каждая запись получает уникальный `id`, сгенерированный через [`nanoid`](https://github.com/ai/nanoid) (кроме Temp Voice, где `id` — это ID самого голосового канала, и кроме каналов/категорий папок, где `id` — это ID соответствующего Discord-канала). Записи в памяти кэшируются как `Map`, а запись на диск выполняется атомарно (через временный `.tmp`-файл с последующим `rename`) и последовательно — конкурентные вызовы `set`/`update`/`delete` для одной и той же БД ставятся в очередь, чтобы избежать гонок при записи.

`JsonDb<T>` предоставляет базовый набор методов: `get`, `getAll`, `has`, `find`, `filter`, `query` (по точному совпадению полей), `queryContains` (по вхождению значения в массив), а также асинхронные `set`, `update`, `delete`.

> Директория `db/` создаётся автоматически и не требует ручной настройки. При необходимости добавьте её в `.gitignore`, если она ещё не туда включена — файлы содержат данные конкретного сервера (Discord ID участников, причины отпусков/AFK, владельцы временных комнат, владельцы каналов папок, состав сборов МП и т.д.) и не должны попадать в репозиторий.

## Deployment

1. Соберите проект:

   ```bash
   pnpm build
   ```

2. Запустите собранную версию:

   ```bash
   pnpm start
   ```

3. Для деплоя слэш-команд и/или кастомных эмодзи на боевой сервер:

   ```bash
   pnpm deploy
   pnpm deploy-emojis
   ```

   Для предварительной проверки без реальных изменений:

   ```bash
   pnpm deploy-emojis:dry
   ```

4. После первого деплоя разверните панель Temp Voice командой `!temp` в нужном текстовом канале (см. [Систему временных голосовых каналов](#система-временных-голосовых-каналов-temp-voice)).

Убедитесь, что переменные окружения (`.env`) на продакшн-сервере настроены отдельно от локальных и что `DATABASE_URL` указывает на боевую базу данных. Также убедитесь, что директория `db/` (локальные JSON-записи AFK, отпусков, папки, Temp Voice и сборов МП) сохраняется между деплоями — например, через volume/persistent storage, иначе активные AFK-статусы, отпуска, персональные каналы участников, записи о владельцах временных комнат и текущие сборы МП будут потеряны при пересоздании контейнера.
